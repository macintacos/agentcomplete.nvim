*agentcomplete.txt*	Completion for agent-CLI prompt buffers in Neovim

                                                               *agentcomplete*

				   agentcomplete.nvim ~

Complete an agent CLI's skills, commands, and files inside the prompt buffer
that the CLI opens in Neovim: Claude Code (`Ctrl+G`) and OpenCode (`/editor`).
Works through blink.cmp (auto-detected) or Neovim's built-in completion.

This help covers the concepts and every option. To install the plugin, start
with the README; to work on the plugin itself, see CONTRIBUTING.md.

1. Introduction
                                                  *agentcomplete-introduction*

Agent CLIs let you compose a prompt in your editor. Claude Code opens an
external editor on `Ctrl+G`; OpenCode opens one on `/editor`. agentcomplete
attaches to that prompt buffer and offers exactly the completions that are
useful while writing a prompt:

	`/`	skills and commands available to the agent in this project
	`@`	files and folders under the project root

It also lays the prompt out for writing rather than coding: a centered page
at a readable width (|agentcomplete-composer|), beside the agent's last
message (|agentcomplete-context|).

It does nothing in any other buffer. Outside a detected prompt buffer your
normal completion stack is untouched.

Two completion backends are supported, chosen by the 'backend' option:

	blink.cmp	preferred, auto-detected when installed
	native		Neovim's built-in insert-mode completion

agentcomplete is the only setup completion requires — nothing is installed on
the agent side for it. (|agentcomplete-context| offers OpenCode users one
optional extra; see |:AgentCompleteInstallOpenCodePlugin|.) The plugin reads
the same skill and command directories the agent itself reads, so what it
completes is what the agent can actually run.

2. How detection works
                                                     *agentcomplete-detection*

agentcomplete recognizes a prompt buffer with per-tool detectors and then
roots discovery at the project directory. The 'detect' option controls whether
detection runs at all (see |agentcomplete-configuration|).

Claude Code ~

Claude Code (`chat:externalEditor`, `Ctrl+G`) writes the prompt to
`<tmpdir>/claude-<uid>/claude-prompt-<uuid>.md` and opens it in `$EDITOR`. The
spawned editor does NOT inherit `CLAUDE_CODE_SESSION_ID`, so detection keys on
the buffer name matching `claude-prompt-<uuid>.md`. The project root is the
editor's working directory.

Skills and commands are discovered from, in order:

	`~/.claude/{skills,commands}` (honors `$CLAUDE_CONFIG_DIR`)
	installed Claude Code plugins (skills as `<plugin>:<skill>`)
	`<project>/.claude/skills` and `<project>/.claude/commands`

Skills are found one level deep, as `<dir>/<name>/SKILL.md`.

OpenCode ~

OpenCode (`/editor`, default `<leader>e`) writes the prompt to a bare
`<tmpdir>/<epoch-millis>.md` file with no tool-specific name. Detection
therefore keys on the environment variable `OPENCODE` being `1` — OpenCode
sets it for every command and the spawned editor inherits it — corroborated by
the buffer basename matching `<digits>.md`, so other files opened in the same
Neovim are not misdetected.

Skills and commands are discovered across OpenCode's config bases — the global
config home (`$XDG_CONFIG_HOME/opencode`, else `~/.config/opencode`), an
optional `$OPENCODE_CONFIG_DIR`, and the project-local `<project>/.opencode`:

	skills under `<base>/{skill,skills}/<name>/SKILL.md`
	markdown commands under `<base>/{command,commands}` (recursively)
	commands in `opencode.json[c]` (the `command` map)
	OpenCode's built-in TUI commands (`/help`, `/models`, `/editor`, …)

Both the singular and plural directory spellings are searched, because
OpenCode itself accepts either.

The built-in TUI commands are hidden by default; enable them with the
`opencode.show_all_builtin_commands` option — see
|agentcomplete-configuration|.

OpenCode resolves more than that filesystem scan can see: skills that are
built in, live under `~/.claude/skills`, or nest deeply as `**/SKILL.md`,
and — most notably — every command contributed by an installed OpenCode
plugin, which lives in OpenCode's package cache and so is reachable by no
config-directory scan at all. agentcomplete asks OpenCode for the
authoritative sets by running `opencode debug skill` and
`opencode debug config` asynchronously (once per project, never blocking
the editor), then merges the results with the filesystem scan,
de-duplicated by name. This is OpenCode-only; disable it with
`opencode.resolve_via_cli = false` — see |agentcomplete-configuration|.

In both tools the project root can be overridden — see
|agentcomplete-project-root|.

3. Installation
                                                  *agentcomplete-installation*

With Neovim's |vim.pack|: >lua
	vim.pack.add({ "https://github.com/macintacos/agentcomplete.nvim" })
	require("agentcomplete").setup({})
< With lazy.nvim: >lua
	{ "macintacos/agentcomplete.nvim", opts = {} }
< Or call `require("agentcomplete").setup({})` with any plugin manager.

                                                         *agentcomplete-setup*
`require("agentcomplete").setup({opts})` merges {opts} over the defaults —
deeply, so a nested table may name one key and leave its siblings at their
defaults — registers the commands in |agentcomplete-commands|, and
when 'enabled' is true, installs an autocommand that attaches to detected
prompt buffers on `VimEnter` and `BufReadPost`. Calling it with no arguments
(`setup({})`) uses the defaults below.

blink.cmp users have one extra, mandatory step: register the provider. See
|agentcomplete-blink|. Native-backend users need nothing more.

4. Configuration
                                                 *agentcomplete-configuration*

The full default configuration, with every option: >lua
	require("agentcomplete").setup({
	  enabled = true,        -- attach automatically on detected buffers
	  backend = "auto",      -- "auto" (blink if present, else native) | "blink" | "native"
	  detect = "auto",       -- "auto" (run detectors) | "always" (force on) | "never"
	  sources = {
	    slash = true,        -- complete /skill and /command
	    file = true,         -- complete @path/to/file
	  },
	  allowed_sources = {},  -- blink only: extra blink sources to keep in detected buffers
	  context = {
	    enabled = true,      -- read-only pane showing the agent's last message
	    min_width = 160,     -- columns at or above which it sits left of the prompt
	    stacked = "above",   -- "above" | "below": which side it takes under min_width
	    rumdl_config = nil,  -- path to a rumdl config file for the pane's formatting
	    keys = {
	      scroll_down = "<S-Down>", -- scroll the pane down a line from the prompt
	      scroll_up = "<S-Up>",     -- scroll it back up
	    },
	  },
	  composer = {
	    enabled = true,      -- write the prompt on a centered page, without a gutter
	    width = 80,          -- columns the prompt and the pane's message wrap at
	  },
	  opencode = {
	    show_all_builtin_commands = false, -- complete interactive built-ins (/help, /models, …)
	    resolve_via_cli = true,            -- also source skills/commands from `opencode debug`
	    install_plugin = false,            -- symlink the session-pointer plugin from setup()
	  },
	})
<
'enabled'		boolean (default `true`). When true, attach
			automatically to detected prompt buffers. When false,
			nothing attaches until you run |:AgentCompleteAttach|,
			and blink's other sources are not suppressed either
			until then.

'backend'		`"auto"` | `"blink"` | `"native"` (default `"auto"`).
			`"auto"` routes through blink.cmp if installed,
			otherwise uses native completion. Force either with
			`"blink"` or `"native"`. See |agentcomplete-blink| and
			|agentcomplete-native|.

'detect'		`"auto"` | `"always"` | `"never"` (default `"auto"`).
			`"auto"` uses the built-in detectors
			(|agentcomplete-detection|). `"always"` forces it
			onto the current buffer regardless of detection.
			`"never"` disables detection entirely.

'sources.slash'		boolean (default `true`). Complete `/skill` and
			`/command` after a leading `/`.

'sources.file'		boolean (default `true`). Complete `@path/to/file`
			after a leading `@`.

'allowed_sources'	string[] (default `{}`). blink only. Extra blink
			source names to keep with agentcomplete in detected
			buffers. See |agentcomplete-suppression|.

'context.enabled'	boolean (default `true`). When true, attaching opens a
			read-only pane showing the agent's last message. See
			|agentcomplete-context|.

'context.min_width'	number (default `160`). Terminal width at or above
			which the context pane sits to the left of the prompt,
			as wide as 'composer.width'; below that, stacked with
			it. Re-checked whenever the terminal is resized.

'context.stacked'	`"above"` | `"below"` (default `"above"`). Which side of
			the prompt the pane takes when the terminal is narrower
			than 'context.min_width' and the two are stacked rather
			than side by side. Unrelated to the wide layout, which
			is always to the left. See |agentcomplete-context|.

'context.rumdl_config'	string (default `nil`). Absolute path to a rumdl config
			file, used to format the message the pane shows. A
			relative path resolves against Neovim's working
			directory, which is the dependence this option exists
			to escape. Left unset, the message is formatted with
			rumdl's own built-in defaults. See
			|agentcomplete-context|.

'context.keys.scroll_down'
			string | `false` (default `<S-Down>`). Key mapped on
			the prompt buffer, normal and insert mode, that
			scrolls the context pane down a line while it is open.
			`false` leaves the key alone. See
			|agentcomplete-context-keys|.

'context.keys.scroll_up'
			string | `false` (default `<S-Up>`). The same,
			scrolling back up.

'composer.enabled'	boolean (default `true`). When true, the prompt window
			drops its gutter, wraps prose inside an inset, and is
			held at 'composer.width' between blank margins, boxed
			in the middle of the screen while there is no last
			message to show beside it. When
			false, it is left exactly as your configuration draws
			it. See |agentcomplete-composer|.

'composer.width'	number (default `80`). Columns of text the prompt wraps
			at, and the context pane's message with it.

'opencode.show_all_builtin_commands'
			boolean (default `false`). When true, OpenCode's
			interactive built-in TUI commands (`/help`, `/models`,
			`/editor`, …) are also completed. They are hidden by
			default because they are TUI affordances, not prompt
			content.

'opencode.resolve_via_cli'
			boolean (default `true`). When true, OpenCode
			prompt buffers also source skills from `opencode
			debug skill` and commands from the `command` map of
			`opencode debug config`, both run asynchronously and
			once per project so the editor never blocks. Results
			merge with the filesystem scan, de-duplicated by
			name, surfacing what the scan alone misses: built-in
			skills, skills under `~/.claude/skills`, and every
			command an installed OpenCode plugin contributes.
			Set to `false` to skip the subprocesses, leaving
			completion to the filesystem scan and the
			`opencode.json[c]` command map. OpenCode-only.

'opencode.install_plugin'
			boolean (default `false`). When true, `setup()`
			performs the same symlink as
			|:AgentCompleteInstallOpenCodePlugin|, reporting only
			when the outcome is something other than "already
			installed" — so a conflict or a failure is reported on
			every launch until you resolve it. Set it in a Neovim
			config synced across machines: the command is a
			one-shot you have to remember on each new machine,
			while `setup()` runs wherever your config does, and
			without the plugin |agentcomplete-context| falls back
			to a `guessed` session.

			Because that config travels to machines that have no
			OpenCode, the flag installs only where `opencode` is
			on your `$PATH`; the command itself is an explicit
			request and installs wherever you type it.
			OpenCode-only.

5. blink.cmp integration
                                                         *agentcomplete-blink*

When 'backend' is `"auto"` and blink.cmp is installed, agentcomplete routes
through it. blink cannot register the provider for you, so you MUST add it to
your blink configuration — otherwise the blink backend has no source and no
completions appear: >lua
	require("blink.cmp").setup({
	  sources = {
	    default = { "agentcomplete", "lsp", "path", "buffer" },
	    providers = {
	      agentcomplete = {
	        name = "agentcomplete",
	        module = "agentcomplete.backends.blink",
	      },
	    },
	  },
	})
< Once registered the provider self-gates: it stays dormant in every buffer
except a detected prompt buffer, so listing it in `default` is harmless
elsewhere.

                                                    *agentcomplete-load-order*
Note: agentcomplete reads blink's config when a prompt buffer opens, not in
setup(), so the two can be set up in either order. blink must be loadable by
then: lazy.nvim loads a lazy blink on the `require`, but a blink added to
the 'runtimepath' on an event (e.g. |InsertEnter|) is not there yet, and
with 'backend' `"auto"` the prompt buffer falls back to native completion.

Prefer zero configuration? Set `backend = "native"` and skip provider
registration entirely (see |agentcomplete-native|).

==============================================================================
6. Only-source suppression
                                                   *agentcomplete-suppression*

In a detected prompt buffer the blink backend makes agentcomplete the ONLY
source: every other source (lsp, path, snippets, buffer, lazydev, …) is
suppressed, so the buffer offers nothing but `/` and `@` completions. Every
other buffer keeps your full completion stack untouched.

To keep specific sources with agentcomplete in detected buffers, list them in
'allowed_sources': >lua
	require("agentcomplete").setup({
	  allowed_sources = { "path" }, -- keep `path` alongside agentcomplete
	})
< 'allowed_sources' re-permits, never registers: each name must already be a
registered blink source in your config. Listing a source that you never
registered has no effect — it cannot conjure a source that does not exist.

==============================================================================
7. Native completion
                                                        *agentcomplete-native*

When 'backend' is `"native"` (or `"auto"` with blink absent), agentcomplete
drives Neovim's built-in insert-mode completion. It sets a buffer-local
'completefunc' and a `TextChangedI` autotrigger that opens the popup via
|complete()| as soon as a `/` or `@` trigger context exists. It also sets
'completeopt' to `menuone,noselect` for that buffer only — your global
'completeopt' is never touched. All of this is removed on detach.

Only-source suppression (see |agentcomplete-suppression|) is a blink concept:
the native backend drives 'completefunc' directly, so there is nothing to
suppress and your other completion mechanisms are left alone.

The native backend needs no provider registration, which makes it the
zero-config choice. Prefix filtering is done by agentcomplete (Neovim does not
fuzzy-filter `completefunc` results).

==============================================================================
8. Project root
                                                  *agentcomplete-project-root*

Detection roots skill, command, and file discovery at the editor's working
directory, which is normally the agent's project root. For non-standard
launches you can override it.

Per launch, exported before starting the agent: >sh
	AGENTCOMPLETE_CWD=/path/to/project
< Statically, in your Neovim configuration: >lua
	vim.g.agentcomplete_cwd = "/path/to/project"
< The environment variable wins over `vim.g.agentcomplete_cwd`; both win over
the editor's working directory.

9. Commands
                                                      *agentcomplete-commands*

                                                        *:AgentCompleteAttach*
:AgentCompleteAttach	Force completion, |agentcomplete-highlighting|, and the
			|agentcomplete-composer| onto the current buffer,
			bypassing detection. Use it when a session is not
			auto-detected (an unusual launch) or when 'enabled' is
			false.

                                                        *:AgentCompleteDetach*
:AgentCompleteDetach	Detach completion, highlighting, and the composer from
			the current buffer, removing the backend, the token
			highlights, the margins, and any buffer-local state
			they installed — the prompt window's own options are
			put back as they were.

                                         *:AgentCompleteInstallOpenCodePlugin*
:AgentCompleteInstallOpenCodePlugin
			Symlink agentcomplete's session-pointer plugin into
			OpenCode's config home, at
			`<config>/plugin/agentcomplete.ts`. The plugin records
			which OpenCode session each process is running, which
			is what lets |agentcomplete-context| show the right
			conversation instead of guessing at it.

			A symlink rather than a copy, so the installed plugin
			follows the checkout when agentcomplete updates. A
			link left by a checkout that has since moved is
			re-pointed at the current one; a regular file at that
			path is yours, and is refused rather than overwritten.

			It does not run from `setup()` unless
			'opencode.install_plugin' asks it to: writing into
			another tool's config directory unasked is a surprise.

10. Completion sources
                                                       *agentcomplete-sources*

A completion is offered only at the start of a non-whitespace run that begins
with the trigger character, so `/` and `@` complete at the start of a word but
not mid-token. Matching is case-insensitive. `/` completion matches a prefix
of the skill or command name. `@` completion matches a prefix of the path on
the native backend, and fuzzy-matches the whole relative path on blink (see
|agentcomplete-native| for why the two differ).

	`/`	Skills (`<dir>/<name>/SKILL.md`) and commands. The menu shows
		the skill or command name and its description. OpenCode's
		built-in TUI commands appear only when
		`opencode.show_all_builtin_commands` is true. A user-defined
		command of the same name as a built-in wins.

	`@`	Files and folders under the resolved project root. Folders
		end in `/` and rank above every file. A folder is offered
		when it holds a file `@` offers or is empty, so gitignored
		folders are not. Accepting a folder inserts a space after
		it, ending the token so the menu closes. On blink,
		`@src/li` finds `src/lib/util.lua`, and the menu keeps
		narrowing as you type past each `/`. Slashes you type are
		separators rather than anchors — they need not line up
		with the ones in the path — so `@.co/grig` still finds
		`.codegraph/.gitignore`.

Which directories are searched for each tool is described in
|agentcomplete-detection|.

11. Highlighting
                                                  *agentcomplete-highlighting*

In an attached prompt buffer, `/` and `@` tokens are highlighted — but only
when they resolve. A token naming a skill, command, or path that does not
exist stays uncolored. There is no "broken token" color: the absence of one is
the signal, and it is how you catch a typo before sending the prompt. A
highlight spans the whole token, the trigger character included. That span is
also exempt from spell checking — it carries `spell = false` — so under
'spell' a filename or skill name does not squiggle as a misspelling, while the
prose around it, and any token that did not resolve, are still checked.

Two groups do the work: `AgentCompleteSkill` for resolving `/` tokens (skills
and commands alike), linked to `Special` by default, and `AgentCompleteFile`
for resolving `@` tokens, linked to `Directory`. Both links are defined with
`default = true`, so your own |nvim_set_hl()| wins and the links themselves
survive the `:hi` `clear` that a colorscheme change runs.

What `@` counts as resolving is deliberately broader than what `@` completion
offers: anything on disk, gitignored files and folders included, where
completion is gitignore-aware. Resolution happens at paint
time, not at attach, so a file or skill created after the buffer opened
highlights on the next repaint; repaints are debounced by about 100ms.

Highlighting is backend-agnostic — identical under blink.cmp and the native
backend — and it follows the 'sources.slash' and 'sources.file' toggles.

Highlighting has no setup() option. Restyle the groups directly — but note
that an explicit highlight, unlike the default links above, does not survive a
colorscheme change, so set it from a |ColorScheme| autocommand if you switch
colorschemes after startup: >lua
	vim.api.nvim_create_autocmd("ColorScheme", {
	  callback = function()
	    vim.api.nvim_set_hl(0, "AgentCompleteFile", { fg = "#7aa2f7" })
	  end,
	})
<

12. Composer
                                                      *agentcomplete-composer*

Attaching turns the prompt window into a page to write on rather than a code
buffer. The prompt is where you compose a message to the agent, so it is set
up the way a chat box or a document is: prose wraps at a readable width, and
nothing around it asks for your attention.

In the prompt window, agentcomplete:

	hides	line numbers, the sign and fold columns, the cursor
		line, and the winbar
	wraps	at word boundaries, with a wrapped list item hanging
		under its text rather than its bullet
	insets	the text four columns from the window's edge
	blanks	the window separators and the `~` rows past the last
		line

A winbar you set globally cannot be switched off for one window, so it is
blanked there instead, leaving an empty row. Your statusline, colorscheme,
spelling, 'textwidth', and keymaps are left alone. Every option is set for
the prompt buffer only (|:setlocal|), so any other buffer opened in that
window looks as it always does, and each is put back by
|:AgentCompleteDetach|.

The text wraps at 'composer.width' columns — 80 by default — however wide the
terminal is. Blank margins either side hold the prompt at that width and keep
it centered: a wide terminal widens the margins, never the lines. The margins
hold nothing: moving the cursor into one puts it back in the prompt, closing
either closes both and lets the prompt take the full width, and quitting the
prompt closes them first, so `:q` still leaves Neovim in one step.

The prompt is boxed in the middle of its column instead of running its full
height. The box starts ten rows tall and grows with your text, staying
centered, until it is a few rows short of the top and bottom edges; past that
the prompt scrolls. It has a rounded border, with a blank row inside it above
your text and another below — where the prompt's own statusline sits, when
each window has one ('laststatus' other than 3). Beside the
|agentcomplete-context| pane the box is centered on the screen's full height;
stacked with it, in the half of the column the pane leaves.

With the |agentcomplete-context| pane open the page reads as a conversation.
On a terminal at least 'context.min_width' columns wide the message sits to
the left of your reply, both at 'composer.width', centered as a pair; when
there is not room for both at full width, they share it evenly. Narrower than
'context.min_width', the two share one centered column, the message above
your reply by default, and the reply's inset lines its text up with the
message's: your reply starts where the message's text does, and wraps two
columns past it, at the width of the message's frame. Everything is
re-placed as the terminal is resized.

Margins open only when the prompt is the only window on the screen, as it is
when Claude Code or OpenCode opens it. |:AgentCompleteAttach| in a session
already split into several windows styles the prompt window but leaves your
layout alone.

Some plugins set a winbar or a 'statuscolumn' on every window they see, and
dropbar.nvim sets its winbar again each time the buffer is written. The
composer takes those two back off the prompt window after the events such
plugins attach on. The other options it only sets once: turn line numbers
back on with `:setlocal number` and they stay on.

The margins draw their background, separators, and statuslines in the
`AgentCompleteMargin` highlight group, linked by default to `Normal` so they
vanish into the rest of the screen. Link it elsewhere to see where they
are: >lua
	vim.api.nvim_set_hl(0, "AgentCompleteMargin", { link = "NormalFloat" })
<
The box's border is drawn in `FloatBorder`, as the pane's is. Its background
is the `AgentCompletePrompt` highlight group, linked by default to
`NormalFloat` — invisible under a colorscheme whose floats have no background
of their own, such as a transparent one. Link it to `Normal` to draw the box
without a tint: >lua
	vim.api.nvim_set_hl(0, "AgentCompletePrompt", { link = "Normal" })
<
                                                         *w:agentcomplete_box*
While the prompt is boxed, its window has `w:agentcomplete_box` set to
`true`, so a plugin that draws over windows can leave the box alone. For
incline.nvim's filename label: >lua
	require("incline").setup {
	  ignore = {
	    wintypes = function(winid, wintype)
	      return vim.w[winid].agentcomplete_box or wintype ~= ""
	    end,
	  },
	}
<
Set 'composer.enabled' to `false` to leave the prompt window exactly as your
own configuration draws it. The context pane still sits to its left at
'composer.width' when there is room, and nothing else is sized.

13. Context pane
                                                       *agentcomplete-context*

Attaching to a prompt buffer opens a read-only pane beside it holding the
agent's last message. Without it a reply is written blind: the buffer the
agent opens for you carries no conversation at all.

The pane goes to the left of the prompt when the terminal is at least
'context.min_width' columns wide — the message, then your reply to it — as
wide as the 'composer.width' your reply wraps at, and stacks with the prompt
when the terminal is narrower than that. It re-places itself as you resize, so
a window dragged narrower restacks rather than leaving both halves too
cramped to read. |agentcomplete-composer| describes the page the two share.

Stacked, the pane goes above the prompt, so the conversation reads top-down:
the message over the reply to it. Set 'context.stacked' to `"below"` to keep
the reply on top instead: >lua
	require("agentcomplete").setup({
	  context = { stacked = "below" },
	})
<
Either way it is drawn as a rounded-border window titled with the agent that
spoke, and footed with the keys that scroll it and a reminder that you cannot
answer here: "<S-Up>/<S-Down> scroll · read-only".

It reads as a document rather than a buffer you act on: no line numbers, no
sign or fold column, and markdown markup concealed. That last one is the point
of the pane rather than a detail of it — markup exists to be edited, and this
is the one markdown in the editor nobody will edit. Everything else about how
the message looks is your own markdown setup, unchanged: the pane sets
`filetype` to `markdown` and lets treesitter and whatever renderer you use
style it exactly as they style any other markdown.

It holds a scratch buffer — unnamed, never written anywhere, wiped when it
closes — with 'modifiable' off, so you can move the cursor in to read or copy
but never type. The cursor starts in the prompt buffer.

                                                  *agentcomplete-context-keys*
A message longer than one screen is read from the prompt itself: `<S-Down>`
scrolls the pane down a line and `<S-Up>` back up, in normal and insert mode
both; hold either to keep going. Reaching it any other way means moving the
cursor into the pane and back, which you cannot do without dropping out of
the reply you are composing. Lines are counted as the pane draws them, so a
long paragraph it wraps scrolls a row at a time rather than all at once.
Whichever of the two is configured is named in the pane's footer, which
falls back to `read-only` alone when neither is.

Both are 'context.keys', and either may be set to `false` to leave that key
alone: >lua
	require("agentcomplete").setup({
	  context = {
	    keys = { scroll_down = "<PageDown>", scroll_up = false },
	  },
	})
<
The mappings are buffer-local to the prompt and last only as long as the
pane, so they shadow `<S-Down>` and `<S-Up>` nowhere else. Inside the prompt
they do shadow Vim's own paging — though the prompt itself has little to
page, holding only the reply you are writing.

The pane belongs to the prompt and goes when the prompt does. Quitting the
prompt window dismisses the pane first, so `:q` returns you to the agent
instead of leaving you in a message you cannot reply to; you never have to
close the pane yourself.

When `rumdl` is on $PATH the message is formatted before being shown, with
rumdl's own built-in defaults — prose is left unwrapped and the pane wraps it
to its own width, and no `.rumdl.toml` near the editor's working directory is
consulted, so the pane reads the same whichever project you are in. Point
'context.rumdl_config' at a config file to format with your own rules instead.
A missing binary or a failed run — an unreadable 'context.rumdl_config' among
them — shows the raw message instead: formatting never costs you the pane. The
fallback is recorded in the log named below.

Claude Code has an `externalEditorContext` setting of its own that renders
recent conversation into the prompt buffer, above a "Write your reply below
this line" delimiter. agentcomplete opens no pane in a Claude Code buffer
holding that delimiter, so the two never show you the same message twice. The
check is Claude-Code-only: an OpenCode prompt that happens to quote the same
sentence still gets its pane.

Resolution fails soft throughout. When the last message cannot be found — no
session file, no transcript, no assistant turn in it — no pane opens, nothing
is raised, and one line explaining why is appended to
`.tmp/agentcomplete-context.log` under the editor's working directory. That
path sits inside your project deliberately: the agent whose message failed to
load is the one that has to read it. A tool with no resolver yet is not a
failure and writes no line at all. |agentcomplete-diagnostics| reports the
state either way, for the current buffer.

For Claude Code the message comes from the session transcript under
`~/.claude/projects`, found by walking up from Neovim's parent process to the
`~/.claude/sessions/<pid>.json` that Claude Code wrote — so the pane works
through an $EDITOR wrapper script as well as a direct launch.

For OpenCode the message is read read-only from OpenCode's own SQLite
database at `~/.local/share/opencode/opencode.db` ($XDG_DATA_HOME is
honored), using `sqlite3` — which must be on $PATH for the pane. Which
session to read is the hard part: OpenCode's external editor inherits
$OPENCODE_PID but no session id, and OpenCode records no mapping between the
two. So the session is resolved down three rungs, and the pane's border names
the one that answered — a guess is never shown as a certainty:

	`$OPENCODE_SESSION_ID`
			The session id straight from the environment. Nothing
			sets this today; it is the cheapest answer if OpenCode
			ever does.
	`pointer file`	A record written by agentcomplete's OpenCode plugin,
			naming the session running in this process tree. See
			|:AgentCompleteInstallOpenCodePlugin|.
	`guessed`	The session in this directory used most recently since
			the OpenCode process started — so a session resumed
			with `--continue` resolves as readily as a fresh one.
			Correct in the ordinary case of one OpenCode per
			project, and wrong when two share a directory — which
			is why it says so in the border.

A `guessed` header means the pane may be showing another conversation. Install
the plugin to replace the guess with a certainty, either with
|:AgentCompleteInstallOpenCodePlugin| or by setting 'opencode.install_plugin'.

14. Diagnostics
                                                   *agentcomplete-diagnostics*

When completion misbehaves in a prompt buffer ("no completions", "wrong
sources", "not detected"), dump the live plugin state and read it back. From
the real prompt buffer the agent opened: >vim
	:AgentCompleteAttach          " optional: force a session if not detected
	:luafile scripts/diagnostics.lua
< `scripts/diagnostics.lua` lives in the plugin's repository and is resolved
relative to the editor's working directory, so run it from a checkout of
agentcomplete (or give the full path to the script).

This writes `.tmp/agentcomplete-diagnostics.md` under the editor's working
directory and prints the report to |:messages|. The report contains:

	Config		configured vs. resolved backend, detect mode,
			'enabled', the 'sources' toggles, 'allowed_sources'
	Detection	whether the buffer is detected, the resolved tool, and
			the skill/command directories discovery searched
	Discovery	counts of skills, commands, and files found
	Highlighting	whether highlighting attached, how many tokens are
			painted, what each group resolves to, and the size
			of the resolved / set
	Context		which resolver ran, which rung of its chain answered,
			the session and transcript it read, the size of the
			message, where session pointers are looked for, and
			why no pane opened
	blink		the only-source suppression diagnosis, ending in a
			single "Likely cause" line
	Environment	the raw detection signals (`OPENCODE`, `AGENT`,
			`CLAUDE_CODE_SESSION_ID`, `$AGENTCOMPLETE_CWD`, …) and
			whether the OpenCode plugin is installed

Contributors running the plugin from a checkout can produce the same report
headlessly with `mise run diag`; see CONTRIBUTING.md.
