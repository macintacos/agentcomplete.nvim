*agentcomplete.txt*	Completion for agent-CLI prompt buffers in Neovim

                                                               *agentcomplete*

				   agentcomplete.nvim ~

Complete an agent CLI's skills, commands, and files inside the prompt buffer
that the CLI opens in Neovim: Claude Code (`Ctrl+G`) and OpenCode (`/editor`).
Works through blink.cmp (auto-detected) or Neovim's built-in completion.

This help covers the concepts and every option. To install the plugin, start
with the README; to work on the plugin itself, see CONTRIBUTING.md.

1. Introduction
                                                  *agentcomplete-introduction*

Agent CLIs let you compose a prompt in your editor. Claude Code opens an
external editor on `Ctrl+G`; OpenCode opens one on `/editor`. agentcomplete
attaches to that prompt buffer and offers exactly the completions that are
useful while writing a prompt:

	`/`	skills and commands available to the agent in this project
	`@`	files under the project root

It does nothing in any other buffer. Outside a detected prompt buffer your
normal completion stack is untouched.

Two completion backends are supported, chosen by the 'backend' option:

	blink.cmp	preferred, auto-detected when installed
	native		Neovim's built-in insert-mode completion

agentcomplete is the only setup required — there is no companion Claude Code
or OpenCode plugin to install on the agent side. The plugin reads the same
skill and command directories the agent itself reads, so what it completes is
what the agent can actually run.

2. How detection works
                                                     *agentcomplete-detection*

agentcomplete recognizes a prompt buffer with per-tool detectors and then
roots discovery at the project directory. The 'detect' option controls whether
detection runs at all (see |agentcomplete-configuration|).

Claude Code ~

Claude Code (`chat:externalEditor`, `Ctrl+G`) writes the prompt to
`<tmpdir>/claude-<uid>/claude-prompt-<uuid>.md` and opens it in `$EDITOR`. The
spawned editor does NOT inherit `CLAUDE_CODE_SESSION_ID`, so detection keys on
the buffer name matching `claude-prompt-<uuid>.md`. The project root is the
editor's working directory.

Skills and commands are discovered from, in order:

	`~/.claude/{skills,commands}` (honors `$CLAUDE_CONFIG_DIR`)
	installed Claude Code plugins (skills as `<plugin>:<skill>`)
	`<project>/.claude/skills` and `<project>/.claude/commands`

Skills are found one level deep, as `<dir>/<name>/SKILL.md`.

OpenCode ~

OpenCode (`/editor`, default `<leader>e`) writes the prompt to a bare
`<tmpdir>/<epoch-millis>.md` file with no tool-specific name. Detection
therefore keys on the environment variable `OPENCODE` being `1` — OpenCode
sets it for every command and the spawned editor inherits it — corroborated by
the buffer basename matching `<digits>.md`, so other files opened in the same
Neovim are not misdetected.

Skills and commands are discovered across OpenCode's config bases — the global
config home (`$XDG_CONFIG_HOME/opencode`, else `~/.config/opencode`), an
optional `$OPENCODE_CONFIG_DIR`, and the project-local `<project>/.opencode`:

	skills under `<base>/{skill,skills}/<name>/SKILL.md`
	markdown commands under `<base>/{command,commands}` (recursively)
	commands in `opencode.json[c]` (the `command` map)
	OpenCode's built-in TUI commands (`/help`, `/models`, `/editor`, …)

Both the singular and plural directory spellings are searched, because
OpenCode itself accepts either.

The built-in TUI commands are hidden by default; enable them with the
`opencode.show_all_builtin_commands` option — see
|agentcomplete-configuration|.

OpenCode resolves more than that filesystem scan can see: skills that are
built in, live under `~/.claude/skills`, or nest deeply as `**/SKILL.md`,
and — most notably — every command contributed by an installed OpenCode
plugin, which lives in OpenCode's package cache and so is reachable by no
config-directory scan at all. agentcomplete asks OpenCode for the
authoritative sets by running `opencode debug skill` and
`opencode debug config` asynchronously (once per project, never blocking
the editor), then merges the results with the filesystem scan,
de-duplicated by name. This is OpenCode-only; disable it with
`opencode.resolve_via_cli = false` — see |agentcomplete-configuration|.

In both tools the project root can be overridden — see
|agentcomplete-project-root|.

3. Installation
                                                  *agentcomplete-installation*

With Neovim's |vim.pack|: >lua
	vim.pack.add({ "https://github.com/macintacos/agentcomplete.nvim" })
	require("agentcomplete").setup({})
< With lazy.nvim: >lua
	{ "macintacos/agentcomplete.nvim", opts = {} }
< Or call `require("agentcomplete").setup({})` with any plugin manager.

                                                         *agentcomplete-setup*
`require("agentcomplete").setup({opts})` merges {opts} over the defaults,
registers the |:AgentCompleteAttach| and |:AgentCompleteDetach| commands, and
when 'enabled' is true, installs an autocommand that attaches to detected
prompt buffers on `VimEnter` and `BufReadPost`. Calling it with no arguments
(`setup({})`) uses the defaults below.

blink.cmp users have one extra, mandatory step: register the provider. See
|agentcomplete-blink|. Native-backend users need nothing more.

4. Configuration
                                                 *agentcomplete-configuration*

The full default configuration, with every option: >lua
	require("agentcomplete").setup({
	  enabled = true,        -- attach automatically on detected buffers
	  backend = "auto",      -- "auto" (blink if present, else native) | "blink" | "native"
	  detect = "auto",       -- "auto" (run detectors) | "always" (force on) | "never"
	  sources = {
	    slash = true,        -- complete /skill and /command
	    file = true,         -- complete @path/to/file
	  },
	  allowed_sources = {},  -- blink only: extra blink sources to keep in detected buffers
	  opencode = {
	    show_all_builtin_commands = false, -- complete interactive built-ins (/help, /models, …)
	    resolve_via_cli = true,            -- also source skills/commands from `opencode debug`
	  },
	})
<
'enabled'		boolean (default `true`). When true, attach
			automatically to detected prompt buffers. When false,
			nothing attaches until you run |:AgentCompleteAttach|.

'backend'		`"auto"` | `"blink"` | `"native"` (default `"auto"`).
			`"auto"` routes through blink.cmp if installed,
			otherwise uses native completion. Force either with
			`"blink"` or `"native"`. See |agentcomplete-blink| and
			|agentcomplete-native|.

'detect'		`"auto"` | `"always"` | `"never"` (default `"auto"`).
			`"auto"` uses the built-in detectors
			(|agentcomplete-detection|). `"always"` forces it
			onto the current buffer regardless of detection.
			`"never"` disables detection entirely.

'sources.slash'		boolean (default `true`). Complete `/skill` and
			`/command` after a leading `/`.

'sources.file'		boolean (default `true`). Complete `@path/to/file`
			after a leading `@`.

'allowed_sources'	string[] (default `{}`). blink only. Extra blink
			source names to keep with agentcomplete in detected
			buffers. See |agentcomplete-suppression|.

'opencode.show_all_builtin_commands'
			boolean (default `false`). When true, OpenCode's
			interactive built-in TUI commands (`/help`, `/models`,
			`/editor`, …) are also completed. They are hidden by
			default because they are TUI affordances, not prompt
			content.

'opencode.resolve_via_cli'
			boolean (default `true`). When true, OpenCode
			prompt buffers also source skills from `opencode
			debug skill` and commands from the `command` map of
			`opencode debug config`, both run asynchronously and
			once per project so the editor never blocks. Results
			merge with the filesystem scan, de-duplicated by
			name, surfacing what the scan alone misses: built-in
			skills, skills under `~/.claude/skills`, and every
			command an installed OpenCode plugin contributes.
			Set to `false` to skip the subprocesses, leaving
			completion to the filesystem scan and the
			`opencode.json[c]` command map. OpenCode-only.

5. blink.cmp integration
                                                         *agentcomplete-blink*

When 'backend' is `"auto"` and blink.cmp is installed, agentcomplete routes
through it. blink cannot register the provider for you, so you MUST add it to
your blink configuration — otherwise the blink backend has no source and no
completions appear: >lua
	require("blink.cmp").setup({
	  sources = {
	    default = { "agentcomplete", "lsp", "path", "buffer" },
	    providers = {
	      agentcomplete = {
	        name = "agentcomplete",
	        module = "agentcomplete.backends.blink",
	      },
	    },
	  },
	})
< Once registered the provider self-gates: it stays dormant in every buffer
except a detected prompt buffer, so listing it in `default` is harmless
elsewhere.

                                                    *agentcomplete-load-order*
Note: call `require("agentcomplete").setup()` AFTER `blink.cmp` is set up.
With lazy.nvim, make agentcomplete depend on blink (or order the specs) so
blink is configured first.

Prefer zero configuration? Set `backend = "native"` and skip provider
registration entirely (see |agentcomplete-native|).

6. Only-source suppression
                                                   *agentcomplete-suppression*

In a detected prompt buffer the blink backend makes agentcomplete the ONLY
source: every other source (lsp, path, snippets, buffer, lazydev, …) is
suppressed, so the buffer offers nothing but `/` and `@` completions. Every
other buffer keeps your full completion stack untouched.

To keep specific sources with agentcomplete in detected buffers, list them in
'allowed_sources': >lua
	require("agentcomplete").setup({
	  allowed_sources = { "path" }, -- keep `path` alongside agentcomplete
	})
< 'allowed_sources' re-permits, never registers: each name must already be a
registered blink source in your config. Listing a source that you never
registered has no effect — it cannot conjure a source that does not exist.

==============================================================================
7. Native completion
                                                        *agentcomplete-native*

When 'backend' is `"native"` (or `"auto"` with blink absent), agentcomplete
drives Neovim's built-in insert-mode completion. It sets a buffer-local
'completefunc' and a `TextChangedI` autotrigger that opens the popup via
|complete()| as soon as a `/` or `@` trigger context exists. It also sets
'completeopt' to `menuone,noselect` for that buffer only — your global
'completeopt' is never touched. All of this is removed on detach.

Only-source suppression (see |agentcomplete-suppression|) is a blink concept:
the native backend drives 'completefunc' directly, so there is nothing to
suppress and your other completion mechanisms are left alone.

The native backend needs no provider registration, which makes it the
zero-config choice. Prefix filtering is done by agentcomplete (Neovim does not
fuzzy-filter `completefunc` results).

==============================================================================
8. Project root
                                                  *agentcomplete-project-root*

Detection roots skill, command, and file discovery at the editor's working
directory, which is normally the agent's project root. For non-standard
launches you can override it.

Per launch, exported before starting the agent: >sh
	AGENTCOMPLETE_CWD=/path/to/project
< Statically, in your Neovim configuration: >lua
	vim.g.agentcomplete_cwd = "/path/to/project"
< The environment variable wins over `vim.g.agentcomplete_cwd`; both win over
the editor's working directory.

9. Commands
                                                      *agentcomplete-commands*

                                                        *:AgentCompleteAttach*
:AgentCompleteAttach	Force completion and |agentcomplete-highlighting| onto
			the current buffer, bypassing detection. Use it when a
			session is not auto-detected (an unusual launch) or
			when 'enabled' is false.

                                                        *:AgentCompleteDetach*
:AgentCompleteDetach	Detach completion and highlighting from the current
			buffer, removing the backend, the token highlights,
			and any buffer-local state they installed.

10. Completion sources
                                                       *agentcomplete-sources*

A completion is offered only at the start of a non-whitespace run that begins
with the trigger character, so `/` and `@` complete at the start of a word but
not mid-token. Matching is case-insensitive. `/` completion matches a prefix
of the skill or command name. `@` completion matches a prefix of the path on
the native backend, and fuzzy-matches the whole relative path on blink (see
|agentcomplete-native| for why the two differ).

	`/`	Skills (`<dir>/<name>/SKILL.md`) and commands. The menu shows
		the skill or command name and its description. OpenCode's
		built-in TUI commands appear only when
		`opencode.show_all_builtin_commands` is true. A user-defined
		command of the same name as a built-in wins.

	`@`	Files under the resolved project root. On blink, `@src/li`
		finds `src/lib/util.lua`, and the menu keeps narrowing as
		you type past each `/`. Slashes you type are separators
		rather than anchors — they need not line up with the ones
		in the path — so `@.co/grig` still finds
		`.codegraph/.gitignore`.

Which directories are searched for each tool is described in
|agentcomplete-detection|.

11. Highlighting
                                                  *agentcomplete-highlighting*

In an attached prompt buffer, `/` and `@` tokens are highlighted — but only
when they resolve. A token naming a skill, command, or path that does not
exist stays uncolored. There is no "broken token" color: the absence of one is
the signal, and it is how you catch a typo before sending the prompt. A
highlight spans the whole token, the trigger character included. That span is
also exempt from spell checking — it carries `spell = false` — so under
'spell' a filename or skill name does not squiggle as a misspelling, while the
prose around it, and any token that did not resolve, are still checked.

Two groups do the work: `AgentCompleteSkill` for resolving `/` tokens (skills
and commands alike), linked to `Special` by default, and `AgentCompleteFile`
for resolving `@` tokens, linked to `Directory`. Both links are defined with
`default = true`, so your own |nvim_set_hl()| wins and the links themselves
survive the `:hi` `clear` that a colorscheme change runs.

What `@` counts as resolving is deliberately broader than what `@` completion
offers: anything on disk, directories and gitignored files included, where
completion is gitignore-aware and files only. Resolution happens at paint
time, not at attach, so a file or skill created after the buffer opened
highlights on the next repaint; repaints are debounced by about 100ms.

Highlighting is backend-agnostic — identical under blink.cmp and the native
backend — and it follows the 'sources.slash' and 'sources.file' toggles.

Highlighting has no setup() option. Restyle the groups directly — but note
that an explicit highlight, unlike the default links above, does not survive a
colorscheme change, so set it from a |ColorScheme| autocommand if you switch
colorschemes after startup: >lua
	vim.api.nvim_create_autocmd("ColorScheme", {
	  callback = function()
	    vim.api.nvim_set_hl(0, "AgentCompleteFile", { fg = "#7aa2f7" })
	  end,
	})
<

12. Diagnostics
                                                   *agentcomplete-diagnostics*

When completion misbehaves in a prompt buffer ("no completions", "wrong
sources", "not detected"), dump the live plugin state and read it back. From
the real prompt buffer the agent opened: >vim
	:AgentCompleteAttach          " optional: force a session if not detected
	:luafile scripts/diagnostics.lua
< `scripts/diagnostics.lua` lives in the plugin's repository and is resolved
relative to the editor's working directory, so run it from a checkout of
agentcomplete (or give the full path to the script).

This writes `.tmp/agentcomplete-diagnostics.md` under the editor's working
directory and prints the report to |:messages|. The report contains:

	Config		configured vs. resolved backend, detect mode,
			'enabled', the 'sources' toggles, 'allowed_sources'
	Detection	whether the buffer is detected, the resolved tool, and
			the skill/command directories discovery searched
	Discovery	counts of skills, commands, and files found
	Highlighting	whether highlighting attached, how many tokens are
			painted, what each group resolves to, and the size
			of the resolved / set
	blink		the only-source suppression diagnosis, ending in a
			single "Likely cause" line
	Environment	the raw detection signals (`OPENCODE`, `AGENT`,
			`CLAUDE_CODE_SESSION_ID`, `$AGENTCOMPLETE_CWD`, …)

Contributors running the plugin from a checkout can produce the same report
headlessly with `mise run diag`; see CONTRIBUTING.md.
